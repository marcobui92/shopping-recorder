# Recorder Data Model and Migration Plan

## Scope

This document defines the persistence contract for recorder identity, packing/unpacking activities, media assets, upload attempts, and provider-neutral storage references. It is the implementation reference for `feat-011` and later provider features.

Recorder migrations `0003`–`0007` are additive and independent of the former shopping scope. The separately approved `feat-019` retirement removes the legacy endpoints/code and drops the empty local `shopping_records` table through forward migration `0008`; it does not alter recorder data.

## Core Invariants

- UUIDs generated by PostgreSQL are the public identifiers for users, activities, assets, attempts, and connected accounts.
- The internal application user ID is the only ownership key. Username, email, and Google identity are mutable metadata and never authorize recorder access.
- An activity selects exactly one storage provider, `s3` or `google_drive`, when it is created. Every asset and upload attempt under it uses that provider.
- An activity is not completed evidence until it owns at least one asset, every asset is `ready`, and the backend accepts the explicit completion transition.
- A media asset is not retrievable evidence until the backend verifies provider existence, byte size, media type, and SHA-256 checksum during finalization.
- Provider object IDs, bucket names, Drive file IDs, upload session IDs, credentials, and provider errors are server-only. Public API resources expose application IDs and stable media metadata.
- Retrying an upload creates a new attempt for the existing asset. It does not create a duplicate asset.
- Lifecycle controls use immediate logical cancellation/deletion plus tracked provider cleanup. The MVP has no automatic expiry; evidence remains until its owner deletes it.

## Entities

### `app_users`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | Primary key, `gen_random_uuid()` |
| `username` | `varchar(64)` | Required; trimmed; 3–64 characters |
| `username_normalized` | `varchar(64)` | Required; lowercase canonical form; unique |
| `email` | `varchar(254)` | Nullable; used only for self-service recovery |
| `password_hash` | `text` | Required Argon2id encoded hash; never returned |
| `status` | `varchar(16)` | `active` or `disabled`; default `active` |
| `created_at` | `timestamptz` | Required; default `now()` |
| `updated_at` | `timestamptz` | Required; default `now()` |

Email is optional and is not an ownership key. Registration, normalization details, and email verification can evolve without changing activity ownership.

### `user_sessions`

| Column | Type | Rules |

A session is valid only when the user is active, `revoked_at` is null, and both expiry timestamps are in the future.

### `recorder_activities`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | Primary key |
| `owner_user_id` | `uuid` | Required FK to `app_users(id)`; indexed with creation time |
| `operation_type` | `varchar(16)` | `packing` or `unpacking` |
| `status` | `varchar(16)` | `draft`, `uploading`, `complete`, `cancelled`, or internal-only `deleted` |
| `storage_provider` | `varchar(16)` | `s3` or `google_drive`; immutable after first asset |
| `reference` | `varchar(160)` | Nullable operator reference, package ID, or order label |
| `notes` | `text` | Nullable; maximum 2,000 characters at the API boundary |
| `occurred_at` | `timestamptz` | Required operational timestamp; defaults to server time |
| `completed_at` | `timestamptz` | Nullable; set exactly once on completion |

`UNIQUE (id, storage_provider)` supports a composite foreign key that prevents cross-provider assets. Owner queries use `(owner_user_id, created_at DESC, id DESC)` for stable pagination.

### Lifecycle persistence

`recorder_activity_audit_events` stores append-only owner-scoped `metadata_updated`, `cancelled`, `deleted`, and `cleanup_retried` events. Before/after JSON contains application metadata only and never provider object references, URLs, credentials, or upload capabilities.

`media_cleanup_jobs` stores one server-only cleanup job per activity asset with its exact provider object/version reference, attempt count, stable failure classification, and `pending`/`succeeded` state. Logical cancellation/deletion commits before provider calls, so access is revoked immediately even during an outage. Owner-authorized retry reprocesses only pending jobs.

### `media_upload_attempts`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | `uuid` | Primary key |
| `asset_id` | `uuid` | Required FK to `media_assets(id)` |
| `attempt_number` | `integer` | Required positive integer; unique per asset |
| `status` | `varchar(24)` | `issued`, `finalizing`, `succeeded`, `failed`, or `expired` |
| `provider_upload_ref` | `text` | Nullable opaque server-only provider upload reference |
| `expires_at` | `timestamptz` | Required capability expiry |
| `failure_code` | `varchar(64)` | Nullable stable internal classification; no secrets |
| `created_at` / `updated_at` | `timestamptz` | Required |

Only one nonterminal attempt may exist per asset. This is enforced by a partial unique index for statuses `issued` and `finalizing`.

## Database Constraint Strategy

- Use `CHECK` constraints for bounded state/provider values instead of PostgreSQL enum types, so later forward migrations can add states without replacing a database type.
- Require `completed_at` exactly when an activity is `complete`; require `ready_at` and all verified media fields exactly when an asset is `ready`.
- Add a partial unique index on `(storage_provider, provider_object_ref)` when the provider reference is not null.
- Keep `ON DELETE RESTRICT` for recorder rows. User deletion is logical: media access is revoked, provider bytes are removed, and the minimal activity/audit tombstone remains for integrity.
- Enforce the selected provider using `UNIQUE (id, storage_provider)` on activities and a composite foreign key from media assets.
- Lock the affected activity, asset, and attempt rows during state transitions so concurrent finalize, retry, and complete requests cannot violate lifecycle invariants.

## Lifecycle Rules

### Activity

```text
draft --first upload attempt--> uploading --explicit completion--> complete --owner delete--> deleted
  \---------------- cancellation ----------------/
```

- `draft` may have no assets.
- `uploading` begins when the first upload attempt is issued and may contain pending, failed, or ready assets.
- `complete` requires at least one asset and requires every asset to be `ready`.
- Metadata (`operation_type`, `reference`, `notes`, and `occurred_at`) may be corrected before or after completion and every correction is audited; storage choice and evidence bytes remain immutable.
- `draft` and `uploading` activities may become `cancelled`; `complete` activities cannot be cancelled.
- Only `complete` activities may become internal-only `deleted`. Deleted activities are immediately absent from list/detail/content APIs.
- Cancellation expires active upload attempts and revokes evidence access before best-effort provider cleanup begins.

### Media asset and attempts

```text
asset: pending_upload -> verifying -> ready
                         |           
                         +-> failed -> new attempt -> verifying

attempt: issued -> finalizing -> succeeded
           |            |
           +-> expired  +-> failed
```

- Creating or retrying an upload returns a short-lived upload capability without exposing provider credentials.
- Finalization is idempotent for the same successful attempt.
- Provider verification failure records a stable failure code and keeps the activity incomplete.
- A stale or expired attempt cannot finalize an asset; the client requests a new attempt.

## Migration Sequence

Existing applied migrations, including `0001_create_schema_migrations.sql` and `0002_create_shopping_records.sql`, remain byte-for-byte unchanged.

1. `0003_create_app_identity.sql` — create `app_users`, `user_sessions`, and `password_reset_tokens`, their checks, unique indexes, and expiry indexes.
2. `0004_create_recorder_activities.sql` — create `recorder_activities`, ownership/provider constraints, and owner-history indexes.
3. `0005_create_media_assets.sql` — create `media_assets` and `media_upload_attempts`, the composite activity/provider foreign key, lifecycle checks, retry uniqueness, and activity/asset indexes.
4. `0006_create_google_drive_connections.sql` — created by `feat-013` after the Google adapter is implemented; add encrypted credential and connection-state persistence without modifying recorder ownership.
5. `0007_add_recorder_lifecycle_controls.sql` — add lifecycle timestamps/states, append-only audit events, and retryable provider cleanup jobs. Number `0006` remains reserved for deferred Google Drive work.
6. `0008_drop_legacy_shopping_records.sql` — separately approved breaking retirement; drop the legacy table after inventorying zero local rows. It has no recorder-table dependency.

Each migration runs transactionally through the existing migration runner. A failed migration is fixed by a new forward migration after release; applied migration files are never edited because the runner verifies checksums. Before applying a destructive migration outside local development, take and verify a database backup. Migration `0008` requires restoring that backup or a separately reviewed forward reconstruction if rollback is required.
